## 2. 仕様のうち、実装して無理があった点

仕様の文面のままでは、実装できないか、仕様自身の例が通らなかった点。どれも DECISIONS で解消した。SPEC.md への反映は、一部が未承認のまま残っている（6 章）。

1. **部分型を「ユニオンの包含に限る」と、§6 の例が型検査を通らない**（B1）。`Element<Keybind>` を `Element<Appearance | Animation | Keybind>[]` に入れるには、配列と Element の共変性が要る。不変なコンテナの共変性を加えた。
2. **「関数の引数と戻り値は注釈が必須」と、§6 の例 `binds.map((b) => …)` が矛盾する**（A3）。組み込みメソッドのコールバックだけ、文脈から推論する。
3. **「呼び出しグラフが DAG」だけでは停止性を保証できない**（B8・B9）。関数を値として渡せる（ポリシーで必須）ので、呼び出しではなく「名前の参照」のグラフにし、さらに再帰型を禁止して自己適用 `f(f)` に型が付かないようにした。こうすると、単純型付きラムダ計算と同じく強正規化性が成り立つ。
4. **リソース上限の表に「構文の入れ子の深さ」がない**（C10）。これがないと、`((((…` が 100 万個並ぶ入力で、パーサや再帰的な処理がスタックを使い切って abort する。「パニックも abort もしない」（§10）と両立しない。上限を足したうえで、数え方を 2 回直した。
   - 左結合の演算子の連鎖も数えないと、`a + a + …` で自前の再帰処理が溢れる。
   - トップレベルの `}` で数え直さないと、関数が 65 個並ぶだけのファイルで上限に当たる（評価の適合テストで発覚）。
5. **オブジェクト型どうしのユニオンの禁止（B2）と、`??` や `?:` の組み合わせ**。`binds[0] ?? fallback` の両辺は別のオブジェクト型になり、そのままユニオンをとると B2 で弾かれる。広いほうの型をとる規則（S4）を足した。
6. **E3 と E4 の境界**（A5）。§10 の例は「未知のキー」が E3、「必須フィールドの欠落」が E4 で、同じ種類の誤りが 2 つの帯に分かれていた。ホストの組み込みコンポーネントに関するものは E4、それ以外は E3 と決めた。
7. **`satisfies` は代入可能性の検査で、§8 の「完全一致」と意味が違う**（A6）。関数型を不変にして、両者を一致させた。
8. **`else` のない `if` は文法では書けるのに、規則（全経路で return）で必ず誤りになる**（A4）。else を必須にした。
9. **リソース上限を超えたときの位置**（D8）。どのノードで上限を超えるかは、ステップの数え方の細部で決まる。適合テストを実装に依存させないため、宣言の位置で報告することにした。
10. **値がないことと `undefined` を区別しない（B7）こと**は、型・評価・ホストの値の検査（`conforms`）の 3 か所で、一貫して扱う必要があった。動的な検査の食い違いを P3 の proptest が見つけた。
11. **JSX の属性文字列**（C13）。§3 の文字列の規則（エスケープあり）と、JSX の意味（エスケープなし、文字参照あり）が合わない。エスケープは JSX に合わせ、文字参照（`&amp;`）は使えないことにした（`&` は E0008。DECISIONS C18）。
12. **ルートの指定がないスキーマ**では、フラグメントをルートにできた。評価器は、ルートが要素であることを前提にしている（P3 が内部エラー E5000 として発見）。ルートの指定がなくても、ルートは 1 つの要素であることを要求した。

使ってみて窮屈だった点（仕様どおりだが、見直す余地がある）:

- **補間と文字列**: テンプレート文字列に `boolean` を補間できない。また、文字列に `length` がない（B15）。例を書くときに何度か引っかかった。
- **リテラル型の比較**: `1 === 2` のような重なりのないリテラル型どうしの比較は E3006（B13 と B3 の組み合わせ）。TypeScript と同じだが、生成テストのジェネレータを直す必要があった。
- **Length の割り算**: Length ÷ Length ができない（B11）。比率を計算したいときに困る。

## 3. 仕様に足りなかった点

DECISIONS の項目の多くが、仕様の沈黙を埋めたもの。実装の判断に必要だった主なもの:

- **型**: `const` の推論とリテラル型の保持（B3）、配列リテラルの要素型（B4）、ユニオンにできる形（B2）、絞り込みの範囲（B14）、`Element<C>` の C とフラグメントの型（B5）、children の渡し方（B6）、ジェネリクスの有無（B10）、型の合わせ方（S4）。
- **式**: 演算子ごとに使える型（B13）、単位つきの値の演算と表現（B11・B12）、組み込みメソッドのシグネチャ（B15）、Record の作り方と参照（B16）、添字の意味（B17）、スプレッドが重なったとき（S1）、条件は boolean だけ（S2）、`%` の符号（D3）。
- **字句と構文**: 許す TypeScript の構文の一覧（C1）、`switch` の細部（C2）、キーワードをプロパティ名に使えるか（C3）、Hooks・イベント属性の判定（C4）、名前の隠蔽（C6）、宣言の評価順（C7）、edition 宣言の厳密な形（C8）、エスケープ・数値・改行の細部（C9）、JSX の子のコメント（C14）。
- **評価**: 数値を文字列にする規則（D1。JS と同じにした）、-0（D2）、ステップの数え方（D4）、値木の span（D6）、誤りで打ち切ること（D9）、内部エラー（D10）。
- **モジュールとホスト**: import の指定子の形（M1）、循環の報告（M2）、段階の進め方（D5・M3）、ライブラリのファイルの規則（E6）、ホストのモジュールが公開できるもの（E4）、値木の変換（E8）、CLI のホスト（H2）。
- **診断と形式**: 診断コード表の持ち方（F1）、診断の JSON（F2）、値木の JSON（D7）。

## 4. oxc_parser を外すときに必要な作業の見積もり

### いまの構成
- `lex.rs`（1,019 行）は自前の字句検査。E0 の検査と、入れ子の深さの前走査を受け持ち、トークン列は作らない。
- `convert.rs`（1,516 行）は、oxc の AST を CDL の AST に変換しながら、CDL にない構文を E1005・E1006・E1007 で弾く。
- oxc の型は `cdl-syntax` の外に出ていない（テストで検査）ので、置き換えの影響は `cdl-syntax` の中だけで済む。

### 作業
1. **字句解析器**: いまの字句検査を、トークン列を作る字句解析器にする。E0 の検査はそのまま使える。JSX のテキストと属性文字列のモード、テンプレートの入れ子、`<` が JSX の開始か比較演算子かの区別は、構文解析器から字句解析器へ文脈を渡す形に変える。約 700 行。
2. **再帰下降の構文解析器**。約 2,000〜2,500 行。
   - 宣言（import・export・const・function・type・interface）とブロック・文。
   - 式は優先順位の上昇法で読む（`?:` `??` `||` `&&` `===` `<` `+` `*`、単項、メンバー・呼び出し・添字、`satisfies`）。
   - JSX と型（ユニオン・配列・タプル・オブジェクト・関数型）。
   - 難所は 2 つ。`(a, b) => …` と括弧の式の区別（先読みかバックトラックが要る）と、`(x) => T` の関数型と括弧の型の区別。自動セミコロン挿入・正規表現・ジェネリクスがないので、TSX 全体よりはずっと小さい。
3. **誤りからの回復**: `;` と `}` で同期して回復し、複数の誤りを報告する（§10。いまは oxc の都合で、最初の構文エラーで止まる）。約 300 行。
4. **入れ子の深さ**: 構文解析器が自分で深さを数えれば、`lex.rs` の前走査（DECISIONS C10 の近似と 2 回の改訂）は要らなくなる。単純化できる。
5. **AST への変換の廃止**: 構文解析器が CDL の AST を直接作るので、`convert.rs` の大半は要らなくなる。ただし、CDL にない構文の診断（E1005・E1006・E1007 とその help）は、構文解析器が「読んで、弾く」形で引き継ぐ必要がある。`let` や `class` などを認識するコードは残る。
6. **適合テストで同じ結果を保証する**: 構文の適合テストのコードと span は変えてはならない。E1001（oxc の一般的な構文エラー）は、span が oxc に依存するので適合テストに入れていない。置き換えのあとに、改めて決める。
7. **Kani と proptest**: 自前の構文解析器は、有界な入力に対して Kani で非パニックを証明できる見込みがある（oxc ではできない）。P1 と P2 はそのまま使える。

### 規模
新しく書くのは約 3,000〜3,500 行で、`lex.rs` と `convert.rs`（計約 2,500 行）を置き換える。適合テストと proptest がそろっているので、作業の大半は構文解析器を書き、テストを通すことになる。1 人で集中して 2〜3 週間、が目安。最大の不確定要素は、矢印関数と括弧の式の曖昧さの扱いと、誤りからの回復の質。

## 6. 残っている課題

- **SPEC.md への反映**: DECISIONS で「仕様: 修正」か「追記」とした項目の多く（C13・C14・C10 の改訂・S1・S2・S4・D8・M1・M3 など）は、SPEC.md に反映していない。
- **プロトタイプの対象外とした仕様の機能**: ホストが公開する定数（§9。DECISIONS X1）と、edition の範囲を問い合わせる API（§13。DECISIONS X2）は実装していない。
- **CLI のスキーマ**: CLI のスキーマは `host:contrast` に固定（H2）。ほかのホストの設定は、CLI では検査できない。
- **構文エラーの扱い**: oxc の構文エラーのメッセージは英語のまま（E1001）。また、誤りから回復しない（4 章）。
- **プロトタイプの対象外**: `fmt`・`migrate`・LSP・パッケージ管理は、プロトタイプの対象外のまま。
